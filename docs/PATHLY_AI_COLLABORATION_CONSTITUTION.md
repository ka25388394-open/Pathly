# Pathly AI 協作控制憲法 v1.0

本文件是 Pathly 專案中所有 AI 協作開發任務的最高控制規則。

任何 Claude / ChatGPT / AI coding assistant 在開始任務前，都必須先讀取本文件，並依照本文件判斷任務邊界。

---

## 1. 核心協作原則

所有開發任務必須遵守：

1. 每次只做最小更動
2. 先盤點，再執行
3. 不重構，除非使用者明確要求
4. 不擴功能，除非使用者明確要求
5. 不優化原始邏輯，除非使用者明確要求
6. 不自行進入下一個 Phase
7. 不處理未被指定的檔案
8. 不使用 `git add .`
9. 不 push，除非使用者明確要求
10. 不碰 `frontend/`，除非使用者明確要求
11. 不碰 `app/` 核心邏輯，除非使用者明確要求
12. 不把整理任務變成開發任務
13. 不把文件任務變成功能任務
14. 不把測試整理任務變成測試重構任務

---

## 2. 任務類型判斷

每次開始前，AI 必須先判斷本次任務類型。

只能選擇以下其中一種主要類型：

- `Inspect only`：只檢查，不修改
- `Move only`：只移動指定檔案，不修改內容
- `Delete only`：只刪除指定檔案
- `Commit only`：只 commit 已確認檔案
- `Test only`：只執行測試，不修改檔案
- `Document only`：只修改指定文件
- `Code change`：修改程式碼
- `Debug`：排查問題，可檢查但不可直接修復，除非使用者要求
- `Planning`：只規劃，不執行

AI 在開始任務前必須回報：

1. 本次任務類型
2. 本次允許動作
3. 本次禁止動作
4. 可碰檔案
5. 不可碰檔案
6. 是否需要使用者確認後才能執行

---

## 3. 檔案權限區

### 綠區：可在明確任務下整理

以下區域可在指定任務中處理，但仍不可越界：

- `docs/`
- `archive/`
- `tools/dev/`
- `scripts/dev/`
- `scripts/ops/`

規則：

- 只能處理使用者指定檔案
- 不可順手整理其他檔案
- 不可使用 `git add .`
- 不可自行 commit，除非任務是 `Commit only`

---

### 黃區：需先盤點，不能直接修改

以下區域必須先做 `Inspect only`：

- `tests/`
- `app/modules/`
- `app/services/`
- `app/core/`
- `app/api/v1/`

規則：

- 先讀取
- 先回報
- 先提出最小方案
- 等使用者確認後才能修改

---

### 紅區：不得碰，除非明確批准

以下區域預設禁止修改：

- `frontend/`
- `/api/v1/ai/support` 相關核心入口
- `app/services/ai/tst_router.py`
- `app/services/ai/level_detector.py`
- `app/main.py`
- `.env`
- `.gitignore`
- database / migration 相關檔案
- 任何 secret / key / local settings

規則：

- 不可修改
- 不可移動
- 不可刪除
- 不可格式化
- 不可重構
- 只有使用者明確指定時才能處理

---

## 4. 執行前檢查

任何任務開始前，AI 必須先確認：

1. 是否需要讀取開發日記
2. 是否需要讀取本協作憲法
3. 是否有今日第一步
4. 是否有禁止事項
5. 是否會碰到 `app/`
6. 是否會碰到 `frontend/`
7. 是否會刪除檔案
8. 是否會 commit
9. 是否會 push
10. 是否可能進入下一個 Phase
11. 是否可能變成重構

若答案涉及高風險動作，必須先停止並回報，不得直接執行。

---

## 5. 執行後越界檢查

每次任務完成後，AI 必須回報：

```md
## 越界檢查

- 是否修改未指定檔案：
- 是否使用 git add .：
- 是否碰 frontend：
- 是否碰 app/：
- 是否新增功能：
- 是否重構：
- 是否進入下一個 Phase：
- 是否刪除檔案：
- 是否產生 commit：
- 是否可以 commit：
- 是否建議 push：
```

## 執行後回報結構

任務完成後，AI 必須按以下結構回報：

```md

- 

### 檔案異動清單
- 新增：
- 修改：
- 刪除：
- 移動：

### 越界檢查
[如上所述]

### 後續建議
[僅在使用者詢問時提供]
```

## 6. commit 前規則

若任務包含 commit：

1. **盤點檢查**：
   - `git status --short`
   - 確認所有 staged 檔案都是意圖修改
   - 確認沒有 unstaged 的意外修改

2. **commit message 規則**：
   - 使用 conventional commits
   - 格式：`type: description`
   - 常用 type：docs, chore, fix, feat

3. **禁止事項**：
   - 禁止 `git add .`
   - 禁止 commit 未指定檔案
   - 禁止 commit sensitive files
   - 禁止 force push

## 7. 每日開發 SOP

### 開始前

1. 讀取本協作憲法
2. 讀取開發日記最新狀態
3. 確認今日第一步
4. 確認今日禁止事項
5. 判斷任務類型與邊界

### 進行中

1. 按任務類型執行
2. 每步驟後檢查越界
3. 必要時停止並詢問

### 收尾時

1. 執行越界檢查
2. 確認檔案異動清單
3. 判斷 commit 可行性
4. 更新開發日記（如需要）
5. 定義明日第一步（如需要）

---

## 8. 例外情況

### 緊急修復

若遇到影響系統運作的緊急問題：

1. 先回報問題範圍
2. 提出最小修復方案
3. 等待使用者確認
4. 執行最小修復
5. 立即測試驗證

### 跨區域任務

若任務需要跨越不同權限區：

1. 分拆為多個子任務
2. 逐一確認每個子任務
3. 按權限順序執行（綠→黃→紅）
4. 每個階段完成後暫停確認

## 9. 常見錯誤與預防

### 錯誤模式

❌ **任務膨脹**：把文件整理變成功能開發
❌ **順手修改**：修改指定檔案時順手改其他檔案  
❌ **git add .**：一次性 stage 所有檔案
❌ **越界重構**：在整理任務中重構程式碼
❌ **自行進 Phase**：沒有確認就進入下一階段

### 預防措施

✅ **任務邊界明確**：開始前先定義任務範圍
✅ **逐步確認**：每步都檢查是否在範圍內
✅ **檔案指定**：明確列出所有會碰的檔案
✅ **分階段執行**：複雜任務分拆為多個階段
✅ **使用者確認**：高風險動作前先詢問
